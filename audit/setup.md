## Hypothesis: confirmed

> `getCircuit` calls `groth16.Setup` lazily per circuit size, in-process, and the same process serves both `/prove` and `/verify`. The verifier trusts a key generated by a process holding the setup randomness, and keys are lost on restart, so the verifying key isn't stable across runs.

The same holds for the ElGamal circuit added in Step 3 (`getElgamalCircuit`).

| Claim | Evidence |
|---|---|
| Setup runs lazily, per circuit size, inside the serving process | `main.go:84-104` (`getCircuit`) and `elgamal.go:131-151` (`getElgamalCircuit`): on the first request for a size n the circuit is compiled, `groth16.Setup(cs)` runs, and `{cs, pk, vk}` goes into an in-memory map. Q4: the first proof takes 2.3× longer than the second, because setup happens inside it |
| One process proves and verifies | The same `cache[n]` supplies `cached.pk` to `groth16.Prove` (`main.go:207`) and `cached.vk` to `groth16.Verify` (`main.go:293, 387`). ElGamal handlers use `elgamalCache` the same way |
| Keys are never saved or loaded | the only serialization in the service is of proofs (`proof.WriteTo` / `proof.ReadFrom`); there's no key file I/O anywhere |
| The verifying key changes with every process | Q1: a proof from instance A fails on instance B of the same binary, for all three verification paths. Q2: it also fails on A after a restart |

## What the verifier actually trusts

**Deployment used by every benchmark in the repo:**
- **One service shared by all.** `fl/compare/experiment.py::_ensure_gnark_service` starts one service, or reuses one already healthy, on `FL_ZKP_SERVICE_URL` (default `http://127.0.0.1:9000`), and the server subprocess and every client subprocess are pointed at that URL (`fl/core/zkp_gnark.py:15`).
- **Clients' proofs and the server's verification go through the same process.** Every client's `/prove`, `/elgamal/prove`, `/elgamal/prove_with` and the server's `/verify`, `/verify_light`, `/elgamal/verify` all hit it.

**What that means:**
1. **The verifier trusts the prover's own service process.** That process ran `groth16.Setup`, so for the moment setup ran it held the toxic waste (τ, α, β, γ, δ). gnark draws these from `crypto/rand` and doesn't expose them, but nothing guarantees they were destroyed. Anyone who controls that process, or modifies the binary, can forge proofs for false statements. In the benchmark this is also the process computing the prover side, so prover and setup authority are the same party.
2. **A split deployment can't work.** If each client ran its own prover service and the server its own verifier (the normal FL arrangement), every honest proof would be rejected: Q1 shows a proof from instance A never verifies on instance B. The integrity mechanism only "works" because prover and verifier share one process, which is precisely the configuration that gives no separation of trust.
3. **Proofs aren't auditable later.**
   - The chain ledger anchors `hash_proof_payload(p)` per proof (`fl/chain.py`), but no verifying key or key identity is recorded anywhere: not in the proof payload, `round_outcomes`, the ledger, or the report.
   - After the service exits, that verifying key no longer exists (Q2). No one can re-verify an anchored proof after the fact, including the stored thesis runs, whose service processes are long gone.
   - The ledger shows which proof bytes were accepted, not that they were valid.
4. **Services reused across runs mix keys silently.** The harness reuses a healthy service (observed in the Step 3/4 smoke runs: PID 9383 served two separate `compare.py` invocations). Proofs from different runs were then verified under one key, while a service restart halfway through a run would make every proof fail. Nothing records which key a run used.

## Is the verifying key stable across restarts?

**No.** Every process start yields new keys for every circuit size (Q2, both circuits):
- **Proofs from one run can't be verified in another**, or after a mid-run restart.
- **Chain anchors can't be checked by anyone after the run.**
- **Stored results can't be re-validated:** the verification outcomes recorded since Step 4 (`round_outcomes`) are the only evidence that proofs verified, and they can't be re-derived.

## Cost of setup today

Setup is paid inside the first proof for each circuit size in each service lifetime:
- Q4, n = 4: 0.32 s vs 0.14 s.
- Measured earlier: the first 128-coordinate ElGamal proof took 31.3 s vs a 3.5 s median (binding.md smoke run), and the first 2000-element norm-circuit proof took 52.4 s vs about 36 s (numbers.md N-2).
- This inflates round-1 prover timings in every stored run whose service started fresh.

## Phase 2 plan (per the Step 6 prompt; for approval)

1. **`gnark_service setup` subcommand.** Compiles each circuit (norm and ElGamal) for each chunk size in a declared list, runs `groth16.Setup` once, and writes `pk` and `vk` per circuit and size.
   - Verifying keys go to a committed, versioned location (e.g. `zkp_gnark_service/keys/<circuit>/<n>.vk`) together with a manifest of circuit identifier, size, constraint count, gnark version, SHA-256 of each vk, and a setup date.
   - Proving keys stay out of git: they're large and aren't needed for verification.
2. **Separate prover and verifier.** A `prove` role that loads `pk` files and serves only proving endpoints, and a `verify` role that loads only `vk` files and serves only verification. The verifier process never has `pk` or the ability to run setup. The Go API refuses lazy setup in both roles (an unknown size is an error, not a trigger for setup).
3. **Pinned identity.** Every proof payload and `round_outcomes` entry records the vk hash it was verified under. The verifier refuses a proof whose declared vk hash doesn't match the manifest entry for that circuit and size, and the ledger anchor includes the vk hash so anchored proofs stay re-verifiable.
4. **Harness.** Start separate prover and verifier services (clients use the prover URL, the server the verifier URL); fail if keys for a required size are missing; never reuse a service across runs without checking the manifest hash.
5. **Documentation** of what a single-party setup does and doesn't guarantee, what a Powers-of-Tau ceremony plus a per-circuit phase-2 contribution would change, and correction of the `docs/ZKP.md` claims above. A real ceremony is out of scope.

**Questions to settle before Phase 2:**
- **Chunk sizes to pre-generate.** The norm circuit uses sizes set by each model's layer and chunk remainders (for example 704, 64, 2000, 48, 32, 2 for healthcare), and ElGamal uses 128 plus remainders. Options are a fixed size list with padding to a fixed chunk size, or generating keys per dataset schema. Padding to one chunk size per circuit keeps the key set small and stable. I recommend it, but it changes proof statements (padded zeros), so the circuits and Step 3/5 tests are touched.
- **Proving-key storage.** ElGamal keys for n = 128 are large. They could be generated on first `setup` and cached outside git, or published as release artifacts.
