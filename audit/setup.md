# Groth16 trusted setup: who generates the keys, and do they survive?

Date: 2026-09-15
Scope: Step 6 Phase 1. `zkp_gnark_service/main.go`, `zkp_gnark_service/elgamal.go`, how the harness deploys the service (`fl/compare/experiment.py`), and whether proofs remain verifiable. **No source files were changed for this report.**

Runtime checks come from [`audit/evidence/setup_evidence.py`](evidence/setup_evidence.py). It starts real instances of the built binary on free ports:

```bash
PYTHONPATH=. python audit/evidence/setup_evidence.py
```

```
Q1  norm circuit: prove on A, verify on A      -> True
    norm circuit: prove on A, verify on B      -> False
    plaintext /verify (hash recomputed) on B    -> False
Q3  elgamal circuit: prove on A, verify on A   -> True
    elgamal circuit: prove on A, verify on B   -> False
Q2  norm circuit: prove on A, restart A, verify -> False
    elgamal: prove on A, restart A, verify      -> False
Q4  first proof for n=4 (includes setup): 0.323 s; second: 0.140 s
```

## Hypothesis: confirmed

> `getCircuit` calls `groth16.Setup` lazily per circuit size, in-process, and the same process serves both `/prove` and `/verify`. The verifier trusts a key generated by a process holding the setup randomness, and keys are lost on restart, so the verifying key isn't stable across runs.

The same holds for the ElGamal circuit added in Step 3 (`getElgamalCircuit`).

| Claim | Evidence |
|---|---|
| Setup runs lazily, per circuit size, inside the serving process | `main.go:84-104` (`getCircuit`) and `elgamal.go:131-151` (`getElgamalCircuit`): on the first request for a size n the circuit is compiled, `groth16.Setup(cs)` runs, and `{cs, pk, vk}` goes into an in-memory map. Q4: the first proof takes 2.3× longer than the second, because setup happens inside it |
| One process proves and verifies | The same `cache[n]` supplies `cached.pk` to `groth16.Prove` (`main.go:207`) and `cached.vk` to `groth16.Verify` (`main.go:293, 387`). ElGamal handlers use `elgamalCache` the same way |
| Keys are never saved or loaded | the only serialization in the service is of proofs (`proof.WriteTo` / `proof.ReadFrom`); there's no key file I/O anywhere |
| The verifying key changes with every process | Q1: a proof from instance A fails on instance B of the same binary, for all three verification paths. Q2: it also fails on A after a restart |

## What the verifier actually trusts

**Deployment used by every benchmark in the repo:**
- **One service shared by all.** `fl/compare/experiment.py::_ensure_gnark_service` starts one service, or reuses one already healthy, on `FL_ZKP_SERVICE_URL` (default `http://127.0.0.1:9000`), and the server subprocess and every client subprocess are pointed at that URL (`fl/core/zkp_gnark.py:15`).
- **Clients' proofs and the server's verification go through the same process.** Every client's `/prove`, `/elgamal/prove`, `/elgamal/prove_with` and the server's `/verify`, `/verify_light`, `/elgamal/verify` all hit it.

**What that means:**
1. **The verifier trusts the prover's own service process.** That process ran `groth16.Setup`, so for the moment setup ran it held the toxic waste (τ, α, β, γ, δ). gnark draws these from `crypto/rand` and doesn't expose them, but nothing guarantees they were destroyed. Anyone who controls that process, or modifies the binary, can forge proofs for false statements. In the benchmark this is also the process computing the prover side, so prover and setup authority are the same party.
2. **A split deployment can't work.** If each client ran its own prover service and the server its own verifier (the normal FL arrangement), every honest proof would be rejected: Q1 shows a proof from instance A never verifies on instance B. The integrity mechanism only "works" because prover and verifier share one process, which is precisely the configuration that gives no separation of trust.
3. **Proofs aren't auditable later.**
   - The chain ledger anchors `hash_proof_payload(p)` per proof (`fl/chain.py`), but no verifying key or key identity is recorded anywhere: not in the proof payload, `round_outcomes`, the ledger, or the report.
   - After the service exits, that verifying key no longer exists (Q2). No one can re-verify an anchored proof after the fact, including the stored thesis runs, whose service processes are long gone.
   - The ledger shows which proof bytes were accepted, not that they were valid.
4. **Services reused across runs mix keys silently.** The harness reuses a healthy service (observed in the Step 3/4 smoke runs: PID 9383 served two separate `compare.py` invocations). Proofs from different runs were then verified under one key, while a service restart halfway through a run would make every proof fail. Nothing records which key a run used.

## Is the verifying key stable across restarts?

**No.** Every process start yields new keys for every circuit size (Q2, both circuits):
- **Proofs from one run can't be verified in another**, or after a mid-run restart.
- **Chain anchors can't be checked by anyone after the run.**
- **Stored results can't be re-validated:** the verification outcomes recorded since Step 4 (`round_outcomes`) are the only evidence that proofs verified, and they can't be re-derived.

## Cost of setup today

Setup is paid inside the first proof for each circuit size in each service lifetime:
- Q4, n = 4: 0.32 s vs 0.14 s.
- Measured earlier: the first 128-coordinate ElGamal proof took 31.3 s vs a 3.5 s median (binding.md smoke run), and the first 2000-element norm-circuit proof took 52.4 s vs about 36 s (numbers.md N-2).
- This inflates round-1 prover timings in every stored run whose service started fresh.

## Phase 2 plan (per the Step 6 prompt; for approval)

1. **`gnark_service setup` subcommand.** Compiles each circuit (norm and ElGamal) for each chunk size in a declared list, runs `groth16.Setup` once, and writes `pk` and `vk` per circuit and size.
   - Verifying keys go to a committed, versioned location (e.g. `zkp_gnark_service/keys/<circuit>/<n>.vk`) together with a manifest of circuit identifier, size, constraint count, gnark version, SHA-256 of each vk, and a setup date.
   - Proving keys stay out of git: they're large and aren't needed for verification.
2. **Separate prover and verifier.** A `prove` role that loads `pk` files and serves only proving endpoints, and a `verify` role that loads only `vk` files and serves only verification. The verifier process never has `pk` or the ability to run setup. The Go API refuses lazy setup in both roles (an unknown size is an error, not a trigger for setup).
3. **Pinned identity.** Every proof payload and `round_outcomes` entry records the vk hash it was verified under. The verifier refuses a proof whose declared vk hash doesn't match the manifest entry for that circuit and size, and the ledger anchor includes the vk hash so anchored proofs stay re-verifiable.
4. **Harness.** Start separate prover and verifier services (clients use the prover URL, the server the verifier URL); fail if keys for a required size are missing; never reuse a service across runs without checking the manifest hash.
5. **Documentation** of what a single-party setup does and doesn't guarantee, what a Powers-of-Tau ceremony plus a per-circuit phase-2 contribution would change, and correction of the `docs/ZKP.md` claims above. A real ceremony is out of scope.

**Questions to settle before Phase 2:**
- **Chunk sizes to pre-generate.** The norm circuit uses sizes set by each model's layer and chunk remainders (for example 704, 64, 2000, 48, 32, 2 for healthcare), and ElGamal uses 128 plus remainders. Options are a fixed size list with padding to a fixed chunk size, or generating keys per dataset schema. Padding to one chunk size per circuit keeps the key set small and stable. I recommend it, but it changes proof statements (padded zeros), so the circuits and Step 3/5 tests are touched.
- **Proving-key storage.** ElGamal keys for n = 128 are large. They could be generated on first `setup` and cached outside git, or published as release artifacts.

**Stopping here, as Step 6 Phase 1 requires.**

## Phase 2: pinned keys, split roles (implemented)

Decisions taken: **one fixed size per circuit with padding**, and **proving keys in a local cache** outside git.

### What changed

| Area | Change |
|---|---|
| `gnark_service setup` (`zkp_gnark_service/keys.go`) | Compiles the norm circuit (n = 256) and the ElGamal circuit (n = 128) and runs `groth16.Setup` once for each. It writes `<circuit>-<n>.vk` and `manifest.json` (circuit, n, constraint count, SHA-256 of vk and pk, gnark version, date, a single-party note) to `--keys-dir`. Proving keys go to `--pk-dir` with mode 0600. It refuses to overwrite existing keys without `--force` |
| `gnark_service serve --role prover\|verifier` | **No lazy setup anywhere.** The prover loads each pk (hash-checked against the manifest), compiles the circuit and checks the constraint count; it serves only `/prove`, `/elgamal/{prove,prove_with,encrypt,decrypt,info}`. The verifier loads only the vks (hash-checked) and serves only `/verify`, `/verify_light`, `/elgamal/{verify,aggregate}`. It never receives `--pk-dir`. Either role exits at startup if a file is missing or its hash differs from the manifest |
| Padding | Norm circuit: values zero-padded to n before hashing, so the hash is over the padded vector and zeros add nothing to Σw². ElGamal circuit: padded slots carry `v = offset` (plaintext 0) with `r = 0`, and the verifier rebuilds the same deterministic padding ciphertexts, so a client can't choose them. Inputs longer than n are refused (400) |
| Pinned identity | Every proof payload carries `vk_sha256`. The client checks that the prover answered under the pinned key. The server rejects a proof whose `vk_sha256` isn't the manifest's, and sends **its own** pinned hash with every verify request; a verifier holding a different key answers 503, which the Python side treats as an infrastructure abort (fail closed, Step 4). The chain anchor hashes the proof payload, so the vk hash is anchored; `round_outcomes` entries record `key_manifest_sha256` |
| Python (`fl/core/gnark_keys.py`, `zkp_gnark.py`, `elgamal_gnark.py`) | `FL_ZKP_PROVER_URL` (:9000) and `FL_ZKP_VERIFIER_URL` (:9001) replace `FL_ZKP_SERVICE_URL`. Chunk sizes come from the manifest; `FL_ZKP_MAX_LAYER_N` and `FL_ELGAMAL_CHUNK` are gone |
| Harness (`fl/compare/experiment.py`) | Fails ZKP modes if the manifest or a proving key is missing. It starts both roles, and reuses a running service only if `/health` reports the expected role **and** manifest hash; anything else on the port (for example the stale pre-Step-6 service that broke run C in Step 5) is killed and replaced |
| Committed keys | `zkp_gnark_service/keys/{manifest.json, norm-256.vk, elgamal-128.vk}` (`.gitignore` negated for that directory) |

### Evidence (`audit/evidence/setup_evidence.py`, rewritten for Phase 2)

The script runs `setup` into a temporary directory (norm n = 8, ElGamal n = 4). It then starts one prover, two verifiers from the same keys, and one verifier from a second, independent setup:

```
Q1  norm: prove on P, verify on V1           -> True
    norm: prove on P, verify on V2           -> True
    plaintext /verify (hash recomputed) on V2 -> True
Q3  elgamal: prove on P, verify on V1        -> True
Q3  elgamal: prove on P, verify on V2        -> True
Q2  norm: prove on P, restart V1, verify     -> True
    elgamal: prove on P, restart V1, verify  -> True
Q4  norm: verify on verifier with other keys -> refused (GnarkServiceError: …/verify_light: HTTP 503)
    elgamal: same                            -> refused (ElGamalServiceError: /elgamal/verify: HTTP 503 verifying key mismatch …)
Q5  POST verifier/prove                      -> HTTP 404
    POST verifier/elgamal/prove              -> HTTP 404
    POST prover/verify_light                 -> HTTP 404
    verifier started without --pk-dir         -> healthy: True
Q6  first proof n=8 (padded): 0.280 s; second: 0.177 s
```

Every Phase 1 failure is reversed: separate processes and restarts verify (Q1–Q3). A different setup is refused loudly rather than silently mixed (Q4), and the roles are separated (Q5). The first-versus-second gap in Q6 is now connection and runtime warm-up only; setup no longer runs inside a request.

The same properties are covered by tests:
- `tests/test_gnark_service_roundtrip.py`: separate verifier, restart, foreign keys → 503, role 404s.
- `zkp_gnark_service/keys_test.go`: setup → load per role, tampered pk/vk refused, overwrite refused, padded ElGamal across separate stores, vk mismatch → 503, oversize → 400.
- All ZKP tests now run against separate prover and verifier processes, using small keys generated per test session (`tests/conftest.py`), never the committed ones.

Results: Go `ok`; Python `103 passed, 1 xfailed` (the xfail is the documented S1-01 CKKS composite).

### Costs and consequences of padding

- **A short chunk now costs the same as a full one.** The prove-time model `t(k) = 0.055 + 15.0 ms·k` in `audit/sampling.md` and `audit/tables/sampling_tradeoff.*` assumed per-size circuits. With padding, each sampled ElGamal chunk costs about t(128) regardless of k, so the sampled-mode proving estimates there are **optimistic for the final partial chunk and must be regenerated** before they're cited. `audit/evidence/sampling_tradeoff.py` now starts a pinned prover, but it hasn't been re-run for this report.
- **The norm chunk shrank from 2,000 to 256 values**, so full `zkp` proves about 8× more, smaller proofs per layer. A larger n means fewer proofs but a bigger proving key and more prover memory. It's one setup flag (`--norm-n`), but changing it re-pins the key.
- **Stored benchmark results predate this change.** Their proving times include in-request setup (Phase 1, "Cost of setup today") and different chunk sizes, so they're not comparable with new runs.

### What a single-party setup guarantees, and what it doesn't

**Guaranteed now:**
- Every prover and verifier uses the *same* published verifying key, identified by hash.
- Proofs stay verifiable after restarts and by independent verifiers, and anyone holding the committed `.vk` can re-check an anchored proof.
- The verifier process never holds proving keys or setup randomness.

**Not guaranteed:** that the setup randomness (τ, α, β, γ, δ) was destroyed.
- It existed in the memory of the one `gnark_service setup` process.
- Whoever ran that process, or tampered with that binary, can forge proofs for false statements (norm bounds, ciphertext binding) that every verifier will accept.
- Pinning makes keys consistent, not trustworthy. Knowledge soundness holds against provers who didn't run setup.

**What a ceremony would change:**
- A Powers-of-Tau phase 1 (universal, reusable, for example the public BN254 transcripts), followed by a per-circuit phase-2 MPC in which several independent parties contribute to δ, makes forgery require collusion of *all* contributors. The manifest would then record the transcript and contribution hashes instead of "single-party".
- gnark v0.10 has an MPC setup package (`backend/groth16/bn254/mpcsetup`), but this repository doesn't use it, and a real ceremony is out of scope.
- Until one is run, claims should read: *"Groth16 with a single-party trusted setup; integrity holds against clients who did not generate the keys."*
